# TODOアプリ V1 要件定義書

## 1. 目的・対象範囲

既存のExpress＋TypeScript＋EJSサイトにTODO管理機能を追加し、一覧表示、登録、完了状態の変更、削除を行えるようにする。データは学生自身のNeon PostgreSQLに保存し、Vercelに公開する。

既存の `/` と `/api/db-check` の動作を維持し、TODO画面を `/todo` に追加する。既存の `db.ts` のDB接続と環境変数 `DATABASE_URL` を使用する。画面からはFetch APIを使用してREST APIを操作する。

V1では認証、優先度、絞り込み、タイトル更新、アプリ独自のレート制限、リアルタイム同期を対象外とする。個人情報は扱わず、架空のデータのみを使用する。認証を設けないため、公開URLへアクセス可能な第三者もTODOを閲覧・登録・変更・削除できる。

TODO機能の新規ファイル配置は要確認とし、設計書で決定する。TodoApiクラスへの分割、DBの物理設計などの実装詳細も設計書で扱う。

## 2. 機能要件・受け入れ条件

### REQ-01 一覧表示

- **操作：** `/todo` を開き、登録済みのTODOを一覧表示する。APIは `GET /api/v1/todos` を使用する。
- **入力：** なし。
- **結果：** APIは200と `data` にTODOの配列を含むJSONを返す。画面ではタイトルと完了状態を確認でき、登録日時が新しい順（同一登録日時の場合はIDの降順）に表示する。0件の場合も200と `{"data": []}` を返し、画面に「TODOがありません」と表示する。
- **エラー：** DB接続障害は503、その他の予期しない内部エラーは500とし、画面にエラーを表示する。
- **受け入れ条件：** 登録済みのTODOが登録日時の降順、同一登録日時の場合はIDの降順で表示され、完了・未完了を区別できること。0件時に正常な空配列と案内表示が得られ、取得失敗を0件と誤認しないこと。
- **確認方法：** 登録日時と完了状態の異なる架空のTODOおよび登録日時が同一のTODOを用意し、APIレスポンスと画面を確認する。0件の場合と、取得失敗の場合も確認する。

### REQ-02 登録

- **操作：** タイトルを入力して登録する。APIは `POST /api/v1/todos` を使用する。
- **入力：** JSONの `title`（文字列、必須）。前後の空白を除去した後、1〜100文字とする。
- **結果：** TODOを未完了の状態で登録し、201と `data` に登録されたTODOを含むJSONを返す。画面の一覧に登録結果を反映し、入力欄をクリアする。登録時の `created_at` と `updated_at` は同一の日時とする。同じタイトルの登録も許可する。TODOの登録件数は全体で最大1,000件とし、完了済みも含めて同時に存在する件数が上限を超えないようにする。上限到達時は登録しない。
- **エラー：** 空の本文・不正なJSONは400、本文上限超過は413、Content-Type違反は415、必須項目不足・型不一致・文字数違反・禁止文字・未定義フィールドは422、DB接続障害は503、その他の予期しない内部エラーは500とする。登録件数上限到達時のステータスは要確認とする。
- **受け入れ条件：** 有効なタイトルが保存され、前後の空白が除去されていること。登録時の `completed` が `false` であり、再読み込みしても登録内容を確認できること。同名のTODOを登録でき、登録成功時に入力欄がクリアされること。登録時の両日時が一致し、不正な入力では登録されないこと。登録件数が1,000件を超えず、上限到達時に登録が拒否され、削除後に空きがあれば登録できること。同時登録でも上限を超えないこと。
- **確認方法：** 1文字、100文字、101文字、空文字、空白のみ、前後に空白のある文字列、タイトルなし、文字列以外、同名タイトル、不正なJSON、未定義フィールド、禁止文字を送信し、ステータス・JSON・一覧・保存結果を確認する。999件からの登録、1,000件での登録拒否、削除後の再登録、999件からの同時登録も確認する。

### REQ-03 完了状態の部分更新

- **操作：** 一覧から対象TODOの完了状態を変更する。APIは `PATCH /api/v1/todos/:id` を使用する。
- **入力：** URLの `id`（3.1のID条件に適合する整数）と、JSONの `completed`（真偽値、必須）。
- **結果：** 完了状態のみを変更し、200と `data` に更新後のTODOを含むJSONを返す。完了から未完了、未完了から完了の両方向に変更可能とし、画面に反映する。完了状態が変化した場合は更新日時も更新し、タイトル・ID・登録日時は変更しない。現在と同じ完了状態を指定した場合は200を返し、更新日時を変更しない。同一TODOへの複数の更新が競合した場合は最後に成功した更新を優先する。更新と削除が競合した場合、削除が先に成立したTODOへの更新は404とし、削除済みデータを復活させない。
- **エラー：** 不正なID・空の本文・不正なJSONは400、本文上限超過は413、Content-Type違反は415、必須項目不足・型不一致・未定義フィールドは422、有効なIDの対象TODOが存在しない場合（削除済みを含む）は404、DB接続障害は503、その他の予期しない内部エラーは500とする。
- **受け入れ条件：** 指定したTODOだけの完了状態を双方向に変更でき、再読み込み後も保持されること。同一状態への更新は200となり更新日時が変化しないこと。競合する更新の結果が最後に成功した更新と一致すること。削除が先に成立した場合は更新が404となり、削除済みTODOが復活しないこと。タイトルの更新はできず、不正な入力でデータが変更されないこと。
- **確認方法：** 同一TODOを未完了から完了、完了から未完了へ変更し、APIレスポンスと再読み込み後の画面を確認する。同一状態への更新前後の日時を比較し、複数のクライアントから競合する更新、および更新と削除を実施して最終状態を確認する。IDが0、負数、小数、指数表記、上限超過、非数値の場合、存在しないID、`completed` の欠落・型不一致、`title` を含むJSON、不正なJSONも確認する。

### REQ-04 削除

- **操作：** 一覧から対象TODOの削除を選択し、確認ダイアログで承認する。APIは `DELETE /api/v1/todos/:id` を使用する。キャンセル時は削除しない。
- **入力：** URLの `id`（3.1のID条件に適合する整数）。リクエスト本文は不要とする。
- **結果：** 対象TODOをDBから物理削除し、204を返す。削除済みIDは再利用しない。レスポンス本文は含めない。削除したTODOは画面の一覧から除かれる。
- **エラー：** 不正なIDは400、有効なIDの対象TODOが存在しない場合は404、DB接続障害は503、その他の予期しない内部エラーは500とする。
- **受け入れ条件：** 確認ダイアログで承認した場合のみ画面から削除を実行し、指定したTODOだけが削除されること。204の本文が空であり、再読み込みしても表示されないこと。キャンセル時は削除されず、存在しないIDの削除は404となること。削除後の新規登録で削除済みIDが再利用されないこと。
- **確認方法：** 複数のTODOを登録し、削除の承認とキャンセルを確認する。APIの204と空の本文、削除後の一覧、再読み込み結果を確認する。不正なID、存在しないID、同一IDの再削除、削除後に新規登録したTODOのIDが再利用されないことも確認する。

## 3. 共通のデータ・エラー条件

### 3.1 TODOデータ

| 項目 | 型 | 条件 |
| --- | --- | --- |
| `id` | 整数 | 1〜2,147,483,647。登録時に付与し、TODOを一意に識別する。削除済みIDは再利用しない。 |
| `title` | 文字列 | 前後の空白を除去した後、1〜100文字。同名登録可。 |
| `completed` | 真偽値 | `true` は完了、`false` は未完了。初期値は `false`。 |
| `created_at` | 日時 | 登録日時。APIではISO 8601形式のUTC文字列。 |
| `updated_at` | 日時 | 更新日時。APIではISO 8601形式のUTC文字列。登録時は登録日時と同一。 |

タイトルの文字数はUnicodeコードポイント数で数える。Unicode正規化は行わない。NUL文字（U+0000）および孤立サロゲートを含むタイトルは422とする。前後の空白除去後、タイトル内に改行またはタブが残る場合も422とする。HTMLタグを含むタイトルは文字列として許可するが、画面ではHTMLとして解釈・実行されないように安全に表示する。入力可能な項目は各操作で定義したものに限定し、POST・PATCHのJSONに未定義フィールドが含まれる場合は422とする。URLのIDは先頭にゼロを付けない10進整数表記（ASCII数字のみ）に限定し、小数表記・指数表記・先頭ゼロ付き表記は400とする。タイトルやIDなどの入力による意図しないSQLの実行（SQLインジェクション）を防止する。

### 3.2 API成功レスポンス

DELETE成功時を除き、成功レスポンスはJSONとし、トップレベルの `data` に結果を格納する。POST・PATCHのリクエストには `Content-Type: application/json` を要求する。異なるContent-Typeまたは未指定時は415とする。POST・PATCHのリクエスト本文の上限は8KiB（8,192バイト）とし、上限超過は413、空の本文は400とする。本文はJSONオブジェクトに限定し、構文上正常でも配列・null・文字列・数値・真偽値の場合は422とする。GETの一覧は古いキャッシュを使用せず、最新の取得結果を返す。未定義のAPIパスには404、定義済みパスの未対応HTTPメソッドには405を返す。405では対象パスで許可されるメソッドをAllowヘッダーで示す。HEAD・OPTIONSの扱いは要確認とする。

| メソッド | パス | HTTPステータス | `data` の内容 |
| --- | --- | --- | --- |
| GET | `/api/v1/todos` | 200 | TODOの配列（0件は `[]`） |
| POST | `/api/v1/todos` | 201 | 登録後のTODO |
| PATCH | `/api/v1/todos/:id` | 200 | 更新後のTODO |
| DELETE | `/api/v1/todos/:id` | 204 | 本文なし（JSONを返さない） |

### 3.3 APIエラーレスポンス

アプリケーションが返すTODO APIのエラーは次の共通JSON形式で返す。Vercelやネットワークなど、アプリケーション外部で発生するエラーはこの形式を保証できない。`code` はエラーの種類、`message` は原因を示す文字列とする。DB接続文字列や内部の例外詳細などはレスポンスに含めない。

```json
{
    "error": {
        "code": "VALIDATION_ERROR",
        "message": "入力値が不正です"
    }
}
```

| HTTPステータス | エラーコード | 発生条件 |
| --- | --- | --- |
| 400 | `BAD_REQUEST` | POST・PATCHの本文が空、JSONの構文が不正、またはURLで指定されたIDが3.1の範囲または表記条件に適合しない。 |
| 404 | `NOT_FOUND` | 未定義のAPIパス、または有効なIDで指定されたTODOが存在しない。 |
| 405 | `METHOD_NOT_ALLOWED` | 定義済みパスで未対応のHTTPメソッドが指定された。 |
| 413 | `PAYLOAD_TOO_LARGE` | POST・PATCHのリクエスト本文が8KiBを超えている。 |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | POST・PATCHで指定されたContent-Typeが条件に合わない、または指定されていない。 |
| 422 | `VALIDATION_ERROR` | JSONオブジェクト以外の本文、必須項目不足、型不一致、タイトルの文字数・禁止文字違反、未定義フィールドなど、JSONの入力条件に違反している。 |
| 500 | `INTERNAL_SERVER_ERROR` | DB接続障害以外の予期しないサーバー内部エラー。 |
| 503 | `SERVICE_UNAVAILABLE` | DB接続障害により処理を実行できない。 |

定義済みパスで対応するHTTPメソッドを使用した場合、適用される検証はContent-Type、本文サイズ、JSON構文（空本文を含む）、ID、入力値、DB処理の順とする。複数の条件に違反する場合は先に該当したエラーを返す。登録件数上限時のHTTPステータス・エラーコードは要確認とする。

サーバー側ではエラーをログに記録する。DB接続文字列などの秘密情報はログに含めない。

この共通仕様は `/api/v1/todos` 配下を対象とし、既存の `/` と `/api/db-check` のレスポンス仕様は変更しない。

### 3.4 画面の共通条件

画面からFetch APIで各操作を行い、成功時は結果を一覧へ反映する。一覧取得中は読み込み中であることを表示する。APIエラーや通信失敗時は画面にエラーを表示し、登録入力内容と操作前の表示状態を維持する。登録・更新・削除の通信中は該当操作のボタン等を無効化し、同じ操作の重複実行を防ぐ。通信終了後は再操作可能とする。画面からのAPIリクエストのタイムアウトは30秒とする。登録・更新・削除は自動再試行しない。通信切断やタイムアウト等で変更の成否が不明な場合は、その旨を画面に表示し、一覧を再取得して実際に取得できた状態を反映する。再取得に失敗した場合は最後に確認できた表示状態を維持する。登録結果が不明な場合は入力内容を維持する。

対応ブラウザはGoogle ChromeおよびMicrosoft Edgeの最新版とする。PC・スマートフォンで操作可能なレスポンシブ表示とし、登録・完了状態変更・削除確認等はキーボードだけでも操作可能とする。画面の確認では、APIエラー・通信失敗時の表示と入力・表示状態の維持、操作中の無効化と復帰、読み込み中の表示、登録成功時の入力欄クリア、HTMLタグを含むタイトルの安全な表示、古いキャッシュが使用されないこと、30秒のタイムアウト、変更リクエストの自動再試行がないこと、通信切断後の一覧再取得、PC・スマートフォンでの操作およびキーボード操作も確認する。

### 3.5 公開・セキュリティ条件

`.env` はGitの管理対象外とし、DB接続情報その他の秘密情報はコミットしない。他オリジンからのブラウザAPIアクセスを許可するCORS設定は追加しない。ただし、認証を設けないため、直接のHTTPリクエスト等による第三者の操作を防げるわけではない。

## 4. 環境別確認

Local、Vercel Preview、Vercel Productionの3環境を確認対象とする。PreviewとProductionは同一のNeon DBを参照する。すべての環境で個人情報を入力せず、架空の確認用データを使用する。Localの異常系検証にはPreview・Productionの共有DBと分離された検証用DBを使用する。共有DBの変更時は、PreviewとProductionの両方で既存バージョンとの互換性を維持する。

| 環境 | 確認方法・確認項目 |
| --- | --- |
| Local | `npm ci`、`npm run dev` で起動し、既存の `/` と `/api/db-check`、`/todo`、4つのAPI操作を確認する。正常系・異常系・境界値・画面共通条件を確認する。IDの上下限・表記条件・非再利用、JSONオブジェクト以外の本文、Content-Type、空本文、8KiBの境界値、禁止文字、Unicode正規化を行わないこと、UTC日時、SQLインジェクション対策、キャッシュ、エラーログ、競合更新、削除との競合、登録件数上限、404・405、エラー判定順序、通信障害を確認する。`npm run build` の成功も確認する。 |
| Preview | VercelのPreview URLで既存の2経路とTODO画面・APIの4操作を確認する。`DATABASE_URL` によるDB接続と、操作結果の永続化を確認する。 |
| Production | VercelのProduction URLで既存の2経路とTODO画面・APIの4操作を確認する。`DATABASE_URL` によるDB接続と、操作結果の永続化を確認する。 |

Previewで登録した確認用TODOがProductionでも取得でき、Productionでの変更・削除がPreviewにも反映されることを確認する。Preview・Productionの共有DB全体を初期化せず、確認に使用したTODOのみを削除する。0件時や登録件数上限、DB障害（503）、内部エラー（500）の検証は、共有DBから分離したLocalの検証環境で行う。

自動テストは必須とし、REQ-01〜REQ-04の正常系・異常系・境界値および競合時のデータ整合性を検証する。自動テストの実行先は共有DBから分離し、テストコードの配置・実行方法は設計書で決定する。公開環境では両バージョンとDB変更の互換性、既存機能の維持、秘密情報が公開されていないことも確認する。

### 4.1 要確認事項

- 登録件数上限到達時のHTTPステータスとエラーコード。
- HEAD・OPTIONSの扱い（4操作以外のHTTPメソッドとしての扱い）。
- 30秒の画面側タイムアウトに加え、サーバー・DB側のタイムアウトをどのように設定し、どのエラーを返すか。
