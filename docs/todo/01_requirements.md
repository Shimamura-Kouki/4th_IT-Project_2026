# TODOアプリ V1 要件定義書

## 1. 目的・対象範囲

既存のExpress＋TypeScript＋EJSサイトにTODO管理機能を追加し、一覧表示、登録、完了状態の変更、削除を行えるようにする。データは学生自身のNeon PostgreSQLに保存し、Vercelに公開する。

既存の `/` と `/api/db-check` の動作を維持し、TODO画面を `/todo` に追加する。既存の `db.ts` のDB接続と環境変数 `DATABASE_URL` を使用する。画面からはFetch APIを使用してREST APIを操作する。

V1では認証、優先度、絞り込み、タイトル更新を対象外とする。個人情報は扱わず、架空のデータのみを使用する。

TODO機能の新規ファイル配置は要確認とし、設計書で決定する。TodoApiクラスへの分割、DBの物理設計、日時のJSON表現などの実装詳細も設計書で扱う。

## 2. 機能要件・受け入れ条件

### REQ-01 一覧表示

- **操作：** `/todo` を開き、登録済みのTODOを一覧表示する。APIは `GET /api/v1/todos` を使用する。
- **入力：** なし。
- **結果：** APIは200と `data` にTODOの配列を含むJSONを返す。画面ではタイトルと完了状態を確認でき、登録日時が新しい順に表示する。0件の場合も200と `{"data": []}` を返し、画面に「TODOがありません」と表示する。
- **エラー：** DB接続障害は503、その他の予期しない内部エラーは500とし、画面にエラーを表示する。
- **受け入れ条件：** 登録済みのTODOが新しい順に表示され、完了・未完了を区別できること。0件時に正常な空配列と案内表示が得られ、取得失敗を0件と誤認しないこと。
- **確認方法：** 登録日時と完了状態の異なる架空のTODOを用意し、APIレスポンスと画面を確認する。0件の場合と、取得失敗の場合も確認する。

### REQ-02 登録

- **操作：** タイトルを入力して登録する。APIは `POST /api/v1/todos` を使用する。
- **入力：** JSONの `title`（文字列、必須）。前後の空白を除去した後、1〜100文字とする。
- **結果：** TODOを未完了の状態で登録し、201と `data` に登録されたTODOを含むJSONを返す。画面の一覧に登録結果を反映する。同じタイトルの登録も許可する。
- **エラー：** 不正なJSONは400、必須項目不足・型不一致・文字数違反・未定義フィールドは422、DB接続障害は503、その他の予期しない内部エラーは500とする。
- **受け入れ条件：** 有効なタイトルが保存され、前後の空白が除去されていること。登録時の `completed` が `false` であり、再読み込みしても登録内容を確認できること。同名のTODOを登録でき、不正な入力では登録されないこと。
- **確認方法：** 1文字、100文字、101文字、空文字、空白のみ、前後に空白のある文字列、タイトルなし、文字列以外、同名タイトル、不正なJSON、未定義フィールドを送信し、ステータス・JSON・一覧・保存結果を確認する。

### REQ-03 完了状態の部分更新

- **操作：** 一覧から対象TODOの完了状態を変更する。APIは `PATCH /api/v1/todos/:id` を使用する。
- **入力：** URLの `id`（1以上の整数）と、JSONの `completed`（真偽値、必須）。
- **結果：** 完了状態のみを変更し、200と `data` に更新後のTODOを含むJSONを返す。完了から未完了、未完了から完了の両方向に変更可能とし、画面に反映する。更新日時も更新対象とし、タイトル・ID・登録日時は変更しない。
- **エラー：** 不正なID・不正なJSONは400、必須項目不足・型不一致・未定義フィールドは422、有効なIDの対象TODOが存在しない場合は404、DB接続障害は503、その他の予期しない内部エラーは500とする。
- **受け入れ条件：** 指定したTODOだけの完了状態を双方向に変更でき、再読み込み後も保持されること。タイトルの更新はできず、不正な入力でデータが変更されないこと。
- **確認方法：** 同一TODOを未完了から完了、完了から未完了へ変更し、APIレスポンスと再読み込み後の画面を確認する。IDが0、負数、小数、文字列の場合、存在しないID、`completed` の欠落・型不一致、`title` を含むJSON、不正なJSONも確認する。

### REQ-04 削除

- **操作：** 一覧から対象TODOの削除を選択し、確認ダイアログで承認する。APIは `DELETE /api/v1/todos/:id` を使用する。キャンセル時は削除しない。
- **入力：** URLの `id`（1以上の整数）。リクエスト本文は不要とする。
- **結果：** 対象TODOをDBから物理削除し、204を返す。レスポンス本文は含めない。削除したTODOは画面の一覧から除かれる。
- **エラー：** 不正なIDは400、有効なIDの対象TODOが存在しない場合は404、DB接続障害は503、その他の予期しない内部エラーは500とする。
- **受け入れ条件：** 確認ダイアログで承認した場合のみ画面から削除を実行し、指定したTODOだけが削除されること。204の本文が空であり、再読み込みしても表示されないこと。キャンセル時は削除されず、存在しないIDの削除は404となること。
- **確認方法：** 複数のTODOを登録し、削除の承認とキャンセルを確認する。APIの204と空の本文、削除後の一覧、再読み込み結果を確認する。不正なID、存在しないID、同一IDの再削除も確認する。

## 3. 共通のデータ・エラー条件

### 3.1 TODOデータ

| 項目 | 型 | 条件 |
| --- | --- | --- |
| `id` | 整数 | 1以上。登録時に付与し、TODOを一意に識別する。 |
| `title` | 文字列 | 前後の空白を除去した後、1〜100文字。同名登録可。 |
| `completed` | 真偽値 | `true` は完了、`false` は未完了。初期値は `false`。 |
| `created_at` | 日時 | 登録日時。 |
| `updated_at` | 日時 | 更新日時。 |

タイトルの文字数はUnicodeコードポイント数で数える。HTMLタグを含むタイトルは文字列として許可するが、画面ではHTMLとして解釈・実行されないように安全に表示する。入力可能な項目は各操作で定義したものに限定し、POST・PATCHのJSONに未定義フィールドが含まれる場合は422とする。

### 3.2 API成功レスポンス

DELETE成功時を除き、成功レスポンスはJSONとし、トップレベルの `data` に結果を格納する。

| メソッド | パス | HTTPステータス | `data` の内容 |
| --- | --- | --- | --- |
| GET | `/api/v1/todos` | 200 | TODOの配列（0件は `[]`） |
| POST | `/api/v1/todos` | 201 | 登録後のTODO |
| PATCH | `/api/v1/todos/:id` | 200 | 更新後のTODO |
| DELETE | `/api/v1/todos/:id` | 204 | 本文なし（JSONを返さない） |

### 3.3 APIエラーレスポンス

TODO APIのエラーは次の共通JSON形式で返す。`code` はエラーの種類、`message` は原因を示す文字列とする。DB接続文字列や内部の例外詳細などはレスポンスに含めない。

```json
{
    "error": {
        "code": "VALIDATION_ERROR",
        "message": "入力値が不正です"
    }
}
```

| HTTPステータス | エラーコード | 発生条件 |
| --- | --- | --- |
| 400 | `BAD_REQUEST` | JSONの構文が不正、またはURLで指定されたIDが1以上の整数ではない。 |
| 422 | `VALIDATION_ERROR` | 必須項目不足、型不一致、タイトルの文字数違反、未定義フィールドなど、JSONの入力条件に違反している。 |
| 404 | `NOT_FOUND` | 有効なIDで指定されたTODOが存在しない。 |
| 500 | `INTERNAL_SERVER_ERROR` | DB接続障害以外の予期しないサーバー内部エラー。 |
| 503 | `SERVICE_UNAVAILABLE` | DB接続障害により処理を実行できない。 |

この共通仕様は `/api/v1/todos` 配下を対象とし、既存の `/` と `/api/db-check` のレスポンス仕様は変更しない。

### 3.4 画面の共通条件

画面からFetch APIで各操作を行い、成功時は結果を一覧へ反映する。APIエラーや通信失敗時は画面にエラーを表示する。登録・更新・削除の通信中は該当操作のボタン等を無効化し、同じ操作の重複実行を防ぐ。通信終了後は再操作可能とする。

画面の確認では、APIエラー・通信失敗時の表示、操作中の無効化と復帰、HTMLタグを含むタイトルの安全な表示も確認する。

## 4. 環境別確認

Local、Vercel Preview、Vercel Productionの3環境を確認対象とする。PreviewとProductionは同一のNeon DBを参照する。すべての環境で個人情報を入力せず、架空の確認用データを使用する。

| 環境 | 確認方法・確認項目 |
| --- | --- |
| Local | `npm ci`、`npm run dev` で起動し、既存の `/` と `/api/db-check`、`/todo`、4つのAPI操作を確認する。正常系・異常系・境界値・画面共通条件を確認する。`npm run build` の成功も確認する。 |
| Preview | VercelのPreview URLで既存の2経路とTODO画面・APIの4操作を確認する。`DATABASE_URL` によるDB接続と、操作結果の永続化を確認する。 |
| Production | VercelのProduction URLで既存の2経路とTODO画面・APIの4操作を確認する。`DATABASE_URL` によるDB接続と、操作結果の永続化を確認する。 |

Previewで登録した確認用TODOがProductionでも取得でき、Productionでの変更・削除がPreviewにも反映されることを確認する。Preview・Productionの共有DB全体を初期化せず、確認に使用したTODOのみを削除する。0件時やDB障害（503）、内部エラー（500）の検証は、共有DBへの影響がないLocalの検証環境で行う。
